## 0. 阅读方式与编号约定

### 0.1 本文档如何驱动逐步迁移

1. 第 2 章是**功能基线**：每个历史模块、每个界面、每个功能点都有稳定编号，迁移时逐条勾销。

4. 第 6 章是**可验收需求**：每个模块给出 `R-`（需求）与 `AC-`（验收）编号，直接可作为开发任务与测试用例编号。

6. 第 9 章是**阻塞台账**：所有无法从手册确认的内容集中登记，迁移到相关阶段前必须闭环。

## 1. 系统概述与迁移目标

### 1.1 历史系统概述（Blade）

Blade 系统用于**有图案晶圆的 2D 综合外观缺陷检测**，具备宏观与微观缺陷检测能力，可检出系统性缺陷与随机缺陷，是半导体封装厂良率管理的基础检测设备（手册 1.1）。

- **适用工艺段**：封装来料检测、电测后检测、划片后检测、重组晶圆检测；适用晶圆裸片与绷铁环蓝膜片。
- **检测部位**：晶圆正面、边缘、背面。
- **可检缺陷**：切割崩边、隐裂、针印、异物、异色、Bump/pad 刮伤、RDL 电路异常、Bump/Die 缺失、Die 偏移等。
- **结果能力**：实时获取缺陷定位信息；AI 辅助缺陷分类；对 Die 给出 OK/NG 判定。
- **支持机型**：`MRS-WI280`（手册 1.2，仅列此一项）。
- **软件构成**：主程序 `Mega.Blade UI`（单一窗口，顶部导航菜单栏进入各模块）+ **独立的 Review 系统**（独立程序快捷方式、独立登录界面、独立权限与密码）。

### 1.2 新系统现状（wafer-inspect-wpf）

依据仓库 `README.md` / `AGENTS.md` / `NavConfiguration.cs` / `MainViewModel.cs`（提交 `f4d1129`）：

| 维度 | 现状 |
|---|---|
| 技术栈 | .NET 10，`net10.0-windows` WinExe / WPF；`WaferInspect.Core`(net10.0) + `WaferInspect.App`；xunit 测试 + Smoke 工具 + GitHub Actions CI |
| 导航 | 单一配置源 `NavConfiguration.cs`，4 组 / 12 项，组可独立折叠并有默认展开状态 |
| 菜单 | 工作台（运行总览、实时监控）／检测业务（检测任务、晶圆地图、缺陷分析、结果报表）／设备与配置（设备管理、配方管理、标定与校验）／系统（告警中心、用户与权限、系统设置） |
| 视图能力 | 5 类：`overview` 总览、`tasks` 任务表、`alarms` 告警、`live` 实时监控、其余 8 个菜单共用「通用数据表」占位视图 |
| 数据 | 1 Hz 模拟数据（DispatcherTimer），未接入真实设备 / 数据库 / 文件系统 |
| 权限 | 无登录、无角色、无权限判定；标题栏仅有 avatar 展示 |
| 硬件 | 无任何设备抽象层（EFEM/ACS/相机/光源/IO/PLC/SECS-GEM 均未建模） |

> 结论：新系统目前是**高保真 UI 骨架**，历史 9 个模块的业务功能基本未实现；迁移工作的主体是把手册中的功能逐条落成真实视图与数据契约，而非替换现有控件。

### 1.6 迁移原则

1. **先骨架后血肉**：先在 Core 层扩展导航/实体契约，再逐模块替换「通用数据表」占位视图。
2. **一功能一落点**：每个 `F-` 功能点在第 5 章映射表中恰好有一个落点；确需复用同一控件时，标为「共享组件」并列出所有引用方。
3. **配置单点**：新增菜单、视图 Key、Bin 类型、默认单位等一律进入 `WaferInspect.Core`，遵守 `AGENTS.md` §2 的单向依赖。
4. **高级功能不丢弃**：手册中标注「推荐忽略」的项按 0.4 级 C 处理，默认收起但必须实现。
5. **每阶段可交付**：阶段结束必须满足 8.3 门禁，禁止把未闭环的 `【待确认】` 带入下一阶段的需求基线。

## 2. 历史系统模块与功能清单

### 2.0 模块职责重组（职责一致性调整）

#### 2.0.1 为什么需要重组

手册第 3 章按**界面入口**划分 9 个模块（3.1~3.9），这是操作手册的组织方式，不是职责边界。按该划分直接迁移会产生以下确定的重复定义与职责交叉：

| # | 重复 / 分散 / 交叉现象 | 历史出现位置 |
|---|---|---|
| D-01 | 「ROI 设置」同一功能被定义两次 | 配方向导 `3.2.2-H` 与首页「算法参数设置 / ROI 参数设置」`3.8.1`（手册明写「将检测配方中的 ROI 设置功能放在首页」） |
| D-02 | 「Map 图上添加/清除扫描区域」同一操作两处实现 | 配方向导 `3.2.2-I` 与算法参数验证 `3.8.1` |

#### 2.0.2 重组原则

1. **职责一致性优先于界面归属**：以「这个功能在做什么」而非「它在哪个页面」定归属。
2. **同一能力唯一 Owner**：任何可复用能力（Map 渲染、图像视窗、轴控制、导出、权限判定）只有一个模块负责定义与维护，其他模块只能消费，不得各实现一份。
3. **配置与执行分离**：配置态（配方、MapType、系统参数）与运行/执行态（扫描、复判、报警处理）分属不同模块，避免配置被运行逻辑改写。
4. **容器与内容分离**：页面布局/视窗容器由承载页面所属模块负责，容器内的数据渲染组件由能力 Owner 提供。
5. **流程编排唯一**：跨能力的多元流程（配方向导、Map 创建、运行配方）由**一个**模块负责编排与步骤门禁，被调用能力不再各自维护一份流程。
6. **业务范围守恒**：只做归并/拆分，不新增、不删除任何 `F-` 功能点；重组前后功能点集合完全相等（见 2.0.6 守恒核对）。

### 3.3 迁移后的统一权限模型（目标态）

| 统一角色 Key | 名称 | 历史来源 | 说明 |
|---|---|---|---|
| `operator` | 操作员 | 主界面 `OP` + Review「操作员」 | 默认登录身份（对齐 2.2 默认 OP） |

1. **单一鉴权点**：登录一次即可访问检测任务、数据分析等所有模块；不得出现第二次登录或第二套密码（C-03）。

4. **Review 权限并入**：`UI-3.9.1` 登录界面取消，改为模块内的权限判定；「复判」「批量复判」「一键 AI 复判」「导出」等操作沿用 3.2 推定矩阵，确认后固化。
5. **审计**：所有配置修改、复判、报警处理必须记录操作人、时间、前后值；手册未要求，属新系统为满足 G-05 引入的最小补充（`【待确认 T-020】` 是否需要审计界面）。

#### 4.9.1 `UI-3.6.1` 报警信息区 / `UI-3.1.9` 日志信息 / `UI-4.2` 报警清除

- **布局**：报警列表（编号、等级、详细信息、开始时间、处理列）+ 蜂鸣器解除按钮 + 日志滚动区。
- **栏位/操作**：`F-3.6.1-01~03`、`F-3.1.9-01~02`、`F-4.2-01~04`、`F-3.1.2-26`。
- **状态与反馈**：机台错误时蜂鸣器与四色灯同时工作并弹出错误信息画面；**第一次**按【报警管理-蜂鸣器解除】清除蜂鸣器声音；低等级警告性错误信息画面**一并被清除**；高等级错误必须手动处理，否则**无法继续使用系统作业**；日志完整文本显示，报错日志核心错误描述**红色字体**；日志时间格式 `MM-DD HH:MM:SS`。
- **数据流**：设备/软件事件 → 统一事件源（本模块）→ 报警列表 + 日志栏 + 运行拦截信号（`H01` 消费）。
- **边界/兼容**：`BR-18` 日志时间格式；`BR-74` 低/高等级报警分支差异；`BR-75` 报警需用户**手动点击处理**才能取消（不自动消失）；`【待确认 T-025】` 报警等级划分规则与四色灯颜色映射。

- **迁移关注点**：新系统当前「告警中心」只有确认/全确认，需补齐等级、蜂鸣器/四色灯、拦截、EFEM 错误清除与日志同源。

#### 4.9.2 `UI-4.1` 错误消息（故障知识库）

- **结构**：每条错误三段式 = ①原因 ②检查项目 ③除错程序（`F-4.1-01~08`）。
- **内容**（须原样保留，不得概括成泛化提示）：
  1. 机台启动开关无法启动 — 总电源未开/急停按钮未打开；检查设备电源总开关、急停；重新执行操作。
  2. 门接近开关无法感应 — 开关故障/线路问题；检查接近开关位置偏差；排除故障后重新执行。
  3. 硅片无法吸紧 — 真空不足/漏气；检查真空表总真空、Chuck 接头、Chuck 硅胶圈压边、Lift-pin 真空；调整后重新执行。
  4. Lift-pin/闸门无法升降 — 真空不足/电磁阀损坏/程序报错；检查压缩空气总开关、Lift-pin 升降电磁阀、PLC 程序；调整后重新执行。
  5. 检测软件启动失败 — 插件启动失败；等待 10s 重启曝光软件测试通信、设备断电重启确认硬件异常；系统初始化后重新执行，仍有问题联系供应商。
  6. 设备拒绝曝光，提示温度或湿度超标 — 设备温度过高；检查无尘室环境温度、设备周围有无热/冷源；排除过热后重新执行。
- **迁移关注点**：以结构化数据（原因/检查项/除错程序）录入，供报警详情直接引用；禁止只做一段静态说明文字。

## 8. 分阶段迁移顺序与完成标准

### 8.1 阶段总览

| 阶段 | 名称 | 主要模块 | 前置 | 核心产出 |
|---|---|---|---|---|
| `P0` | 基线与骨架 | 全部模块的接口/共享组件骨架 | 无 | 14 项导航、数据源与设备抽象层接口、统一鉴权/事件源、`BR-` 断言框架、双向追溯表 |
| `P1` | 检测任务主干（C-01） | `H01` + `H09` 最小闭环 + `H10` 登录 | P0 | 首页 9 栏 + 运行配方状态机完整迁入「检测任务」 |
| `P2` | 配方、对位与算法 | `H02` + `H03` + `H04` + `H05`(MapType) | P1 | 真实配方 CRUD + 10 段向导 + ROI 单一实现 + MapType |
| `P3` | 数据分析（C-02） | `H08` + `H05`(Sinf) + 报表导出 | P1 结果数据 | Review 全量并入「数据分析」，独立子系统消除 |
| `P4` | 设备、图谱与标定 | `H07` + `H06`(标定/公共组件) + `H05`(Wafer 扫描) | P0 设备抽象接口 | 硬件配置单一数据源、标定工具、Map 创建 12 步 |
| `P5` | 系统管理与故障收口 | `H10` 完整 + `H09` 完整 + `X01` | P1~P4 | 统一角色/权限集、报警分级与拦截、故障知识库、全局单位术语 |
| `P6` | 功能等价验收 | 全部 | P1~P5 | `F-`/`BR-`/`AC-` 全量勾销、回归证据、文档与 CI 更新 |

**排序理由**：
1. `P0` 先建共享组件与接口，是为了落实 B-01~B-31 的「唯一 Owner」，避免后续阶段各自实现第二份（这是本次职责重组的核心收益）。
2. `P1` 优先，因为 C-01 是硬约束，且运行态状态机是多数模块的数据来源。
3. `P2` 在 `P1` 后，配方是运行任务的输入；`H03`/`H04` 作为共享能力必须在向导实现时一次做对。
4. `P3` 依赖 `P1` 产出的检测结果；同时兑现 C-02/C-03，越早消除独立子系统越能减少后续双份实现。
5. `P4` 依赖设备抽象层接口（P0 定义、P4 落地实现），不阻塞前面用模拟设备适配器的开发。
6. `P5` 收口权限与报警，因为需要前面所有模块的操作点都已知。
7. `P6` 只做等价性验收，不新增功能。

**模块内跨阶段说明**：`H05` 的 Map 渲染组件属 P0、MapType 属 P2、Sinf 属 P3、Wafer 扫描属 P4；`H06` 的命令层接口属 P0、公共组件属 P2、标定执行属 P4；`H09`/`H10` 先最小闭环（P1）、后完整（P5）。这是能力分层，不违反「同一能力唯一 Owner」。
